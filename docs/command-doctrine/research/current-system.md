# 指揮・対象選択案のための現行コード再調査

読取元：`/workspace/stillveil-myth-lab`。作業ツリーHEADは `87968ea8bb9bf65fdf6b24fed0fa1c70d48a70c4`。今回参照したゲームコードは元の基準 `616a0747c4118a991770226d37347f34b31e2ec6` から変更されていない。以下はコード上の現行挙動で、指揮・服従・統率はまだ実装されていない。

## 先に動画で誤解させない点

1. **現行AIも普通の攻撃は集中しやすい。** SSR軍だけを故意にバラ撃ちさせ、「指揮を使うR軍だけが集中できる」と比較しない。
2. **注視の敵1体は、今は先頭一人の操作へ主に作用する。** すべての味方へ集中命令する機能ではない。
3. **対象の乗っ取り、技の選択、順番の操作、追加行動は別。** 対象だけを変える新案に、無料の新技能やもう一手を混ぜない。
4. **全体攻撃を敵1体へ集中させて4発分に変えるのは別の新技能。** 現行の対象指定だけでは起きない。
5. **通常の挑発は現行にない。** かばうは選ばれた相手への攻撃を実際の受け手で引き受ける処理であり、敵AIの狙いそのものを釣る挑発とは区別する。
6. **低レアに命令コストを低くする等の差を設けるなら新しい設計。** 現行にレアリティ由来の服従率・相性・忠誠値はない。

## A. 対象決定の実態

### 通常攻撃の選好：`src/domain/engine.ts:185-195`

- 眠っていない敵が残っていれば、そちらを優先する。
- aggressive は攻撃力が高い敵を優先。
- survival は敵のhealerを先に並べ、その後は残HPの小さい敵を優先。
- balanced は残HPの小さい敵を優先。同点はUID順。
- したがって複数の通常攻撃が同じ残敵を狙うことは、今のAIでも自然に起きる。

### 役割ごとの技能と対象：`engine.ts:245-333`

|状況・技能|現行の大まかな選好|新しい指揮が変え得るところ|
|---|---|---|
|単体回復|傷ついた味方をHP割合で選ぶ。回復開始の閾値は作戦で変わる（:257-261）|重要な一人へ回復を回す。死亡者は不可。全快者への空打ちを認めるかは別の仕様|
|状態解除|異常や防御低下のある味方を優先（:263-265）|複数の異常者から、次に動く味方などを選び直す|
|2人回復|負傷者のうちHP割合が低い2人（:266-268）|最大2人の集合を保つ。一人へ2回分を束ねる効果ではない|
|強化解除|攻撃強化や再生のある敵、HPが高い側を優先（:269-273）|攻撃班と同じ敵の強化を先に剥がす|
|障壁破壊|有効な障壁の大きい敵（:271-273）|大きさではなく、今回倒したい敵の障壁を狙う|
|かばう|自分以外の低HP味方。既に別のかばうがある相手を避ける（:276-279）|統率役等を意図的に守る。ただし本人をかばう等は許可しない|
|障壁|まだ露出している低HP割合の味方（:281-283）|攻撃を受けそうな重要役へ先に置く|
|再生|再生が付いていない負傷者（:284-286）|長期的に残したい相手へ。既に強い再生がある相手を無理に選ばせるかは要仕様|
|全体強化|生存味方全体（:287-290）|対象の指揮では基本的に増える価値がない|
|星炉|本人以外・ゲージ65以下・未予約の味方から高攻撃力順（:291-293）|条件を満たす受け手のうち、ルネット等へ意図的に回す|
|単体強化|まだ攻撃強化されていない高攻撃力の味方（:294-303）|次に重要な技を撃つ仲間へ宛先を変える|
|状態異常|異常がなく短期耐性もない敵から攻撃力順（:310-312）|攻撃班の対象とは別の敵を眠らせるなど、分担を指示する|
|ジャミング|使える通常技能のある高攻撃力の敵（:313-315）|特定の危険な通常技能を持つ相手に妨害を集中|
|防御低下|まだ低下していない敵から高HP順（:316-319）|残HPが少ない攻撃班の標的へ合わせる|
|範囲役|敵2体以上ならareaを選びやすい（:321-322）|指揮だけで敵1人へ威力を束ねることはない|

**指揮が新しく感じられる例**：通常攻撃の集中そのものより、弱体が高HPの敵へ、攻撃が低HPの敵へ分かれる現行の選好を接続すること。あるいは「攻撃はA、状態異常はB」という分担。なんでも同じ敵へ集めればよいわけではなく、眠らせた敵を殴って起こす等の逆効果もある。

## B. 先頭操作と仲間AIの境界

- `types.ts:9` のPartyOrderは攻撃／防御／必殺、またはskillIdだけ。味方ごとの指揮対象テーブルや服従情報を持たない。
- `application/game.ts:20-25` の `pinCommandTarget` は生存中の**敵**だけを許可する。
- `application/game.ts:158-162` の `focusEnemy` は共通の `battle.focusTargetId` を保存する。
- `application/game.ts:164-180` の `partyOrder` は `battle.partyIds[0]` の先頭一人を検証し、指示を保存する。別の味方へ同じコマンドを渡す仕組みではない。指示の変更は先頭の予約必殺を解除する場合もある。
- `engine.ts:335-365` の `chooseAction` は先頭にだけpartyOrderを渡す。先頭の単体敵対象の通常技能は、focusTargetIdで宛先を変えられる。
- UIも `GameViews.tsx:235-236` で先頭はPartyCommandDial、それ以外は主に必殺予約／回復薬の対象操作。`PartyCommandDial.tsx:27-111` が先頭用の技能選択を実装する。

### 技能の資格・AIの好み・無駄打ちは別

現行の手動回復の`orderTargets`は、生存中の味方から選び、全快でも候補が空になるわけではない。AIは負傷や作戦閾値を見て回復を選ぶが、手動で無駄打ちできる場合がある。2人回復も、手動では生存候補が1人ならその1人へ向く。したがって「現行の対象資格を維持」の一言で、全快者への命令を拒否する仕様まで既存扱いしない。**合法だが無益な命令**を、実行可・事前警告・選択不可のどれにするかは新しい設計。

また`orderTargets`は合法な候補を列挙する関数ではなく、既に優先順で絞られた宛先を返す。新指揮には、技能ごとの候補資格と、AIの好みで選ぶ処理を切り分ける必要がある。

### 現行の手動技能でも、味方の宛先は自動：`party-orders.ts:18-32`

先頭に回復技能を指示しても、好きな仲間を直接選ぶコマンド引数はない。回復等は低HP割合、強化は高攻撃力、星炉は条件付き高攻撃力、全体技能は生存全体へ向く。**「自分が選ぶ技能」と「自分が選ぶ対象」は、現行でも別の自由度**。

## C. 予定表示と、行動が固まる時点

- `companion-behavior.ts:7-17,20-35`：指示待ちの表示は「視線を巡らせる」「武器に手を添える」等の大まかな仕草。私的な予定のskillId・対象を読む表示ではない。
- `engine.ts:380-389`：非先頭の事前コミットメントは、**coordination付きダンジョンに限り**、入力を閉じてRを解決する時に作る。全ダンジョンで常時先に確定していると説明しない。
- `engine.ts:392-400`：事前予定の技能が使えなくなった／予約必殺が使えなくなった場合は予定処理をやめる。対象が全員消えた場合は通常の対象選択へ戻すこともある。
- `engine.ts:531-563`：解決時にコミットメントを作り、通常は行動時の状態を見てAIが選ぶ。状態異常による強制・停止が先に判定され、その後に予定／通常選択が使われる。
- `PartyCommandDial.tsx:119-154`：再生中にはすでに計算されたイベントの技能や宛先を順に見せる。これは解決前に未来を全部見せるものではない。

**新設計の論点**：指揮の成立をいつ判定するか。指示待ちで成功を確定してから盤面を閉じるのか、指揮官の手番で次Rへ予約するのか、味方自身の手番で初めて受領するのか。既存の内部予定へ後から雑に上書きすると、公開した受領表示と実際の行動がズレる。

### 限定された連携の試練は、すでに存在する

`src/content/trials.ts:59-65` の「誓鎖の稽古」は、coordination bonusPercent35を持つ。`engine.ts:418-429` では同じ実際の受け手へ別の味方が攻撃していれば、後続の攻撃へ連携の補正を加える。これは特殊試練のルールで、一般探索の全編成へ常時適用されるものではない。命令の受領・レアリティ別コスト・指揮官との関係が現行にあるわけでもない。新案は、この限定の協撃と何を共有し、何を一般化するのかも区別するとよい。

## D. 必殺予約と対象指揮

- `application/game.ts:238-243`：生存しゲージ100の味方の必殺を、指示待ちにトグル予約する。別の人物の具体的な技へ置換する操作ではない。
- `engine.ts:345-349`：先頭の単体必殺はfocusを使える。非先頭の単体必殺は通常の作戦による敵選好。回復／障壁／全体強化は生存味方全体、area等は敵全体。
- `ultimates.ts:5-11,22-25`：個別名や演出があっても、基本効果は6つの役割契約。全体回復必殺を、指揮だけで一人へ全員分の回復へまとめない。
- `engine.ts:595-620`：必殺でゲージを消費し、役割に応じた既存効果を解決する。

試作を通常の単体敵対象技能に絞れば分かりやすい。単体必殺へ広げる場合も、「予約済みの必殺を別技能に変えず、宛先だけ変える」と区別する。必殺予約の方を指揮の受領より優先するか、併存するかは新しい契約。

## E. かばう・挑発・魅了を区別する

- `types.ts:6-7` と `skill-info.ts:3` にtaunt／挑発テンプレート・状態はない。
- `engine.ts:405-408`：単体攻撃なら、実際のdamage処理で `guardTarget` を持つ別の生存者が受け手になる。
- `engine.ts:421-426`：本人防御の半減、引受軽減、リーダー軽減、障壁等の順に実ダメージを処理する。
- `engine.ts:612,685`：通常areaと範囲必殺はかばう不可。対象を明示しても、この契約は別に残る。
- `engine.ts:227-243,555-563`：睡眠／麻痺で停止し、魅了／混乱で技能と相手を強制的に変える。これは協調的な指揮とは別。新指揮が強制行動へ優先して、睡眠も魅了も無料解除することにならないよう決める。

**例**：指揮で敵術師を狙ったが、敵の護衛がかばう。この時「命令に従わなかった」のではなく、対象決定後にかばわれた。動画の結果ラベルでも、受領失敗とダメージの引受を混同しない。

## F. 石・派生対象・装備窓

- `engine.ts:196-207`：本人の固有技能と装備した石の技能から、CD等を満たすものを取り出す。
- `engine.ts:565-570`：石の威力・処刑等は、実際にその装備石のskillIdを使った時の処理。新しい指揮技能が全員へ石特性を無償配布するわけではない。
- `engine.ts:698-701`：石の技能CD＋装備者の石スロット共通CD。指揮でCDを戻す／別人の石を使わせる／複数回使うのは対象変更と別の効果。
- `engine.ts:707-731`：連鎖は主対象とは別の敵へ出る。慈雨／庇護は低HP割合の味方へ自動で出る。**主攻撃の狙いを変えただけで、副次の宛先まで一括変更しない**。
- `party-orders.ts:22-26`：巻戻しは本人以外で通常技能に待ちがある人、星炉は本人以外・ゲージ65以下、装甲リサイクルはHP75%以下かつ有効障壁等、固有の対象資格がある。指揮は選好を変える場合でも資格を破らない。
- `application/game.ts:135-140`：装備変更は街だけでなく、**ready・round===1・potionUsed=false のWave開始窓**でも許可され、同期後にpartyOrderを削除する。`GameViews.tsx:246` に戦闘中のMemoryGemsモーダルがある。したがって「戦闘中に一切石を替えられない」という説明は不正確。
- `engine.ts:126-135`：Wave開始でfocusや残響を消し、効果とCDをリセットする。新指揮の予約を跨がせるなら別途仕様が要る。

## G. 速度・レアリティ・隊列の実態

- `engine.ts:15-22,49-51`：役割固定速度は守護者18／呪術師15／剣士14／導き手13／癒し手12／詠唱者11。定数が上がっても基礎速度は増えない。
- Rの盾役がSSRの剣士より先に動くことは自然。逆に導き手の指揮官13が、既に動き終わった剣士14へ同じRの命令を後付けするなら、次Rへ予約するか新しい準備段階を設ける必要がある。
- `engine.ts:549`：行動順は速度、tie、UIDで確定する。SSRだからRより早いという式はない。
- `types.ts:3-5,34,42`：R/SR/SSR/XR、役割、強さ等はあるが、信頼・軍階級・服従・訓練値・指揮容量・指揮官との相性はない。
- `engine.ts:49-64`：HP／攻撃／防御は主に役割・定数・リーダー補正を使う。戦闘の対象選択関数にrarityを見て拒否する分岐はない。
- 最大4人のpartyIdsに先頭の意味はあるが、一般的な前衛／後衛の射程や隣接マス戦術はない。「統率軍は10人で、SSR軍は4人」等にするのも別の拡張。

## H. 新しい指揮で最低限決めること

|論点|最初の試作に向く絞り方|
|---|---|
|誰へ命令するか|指揮官以外の生存味方から、人数やコストで上限を決める|
|変える対象|最初は通常の単体敵対象の主技能だけ。技・威力・行動数は変えない|
|行動の費用|指揮官の一手を払う能動技か、LS一枠を払う指示待ち効果かを分ける|
|どこで上書き|AIが合法な技能を決めた後、その技能の合法な候補から主対象を選び直す|
|服従／受領|レアリティで指揮コストを変えるのか、確率を変えるのか、人格ごとの条件も使うのかを混ぜない|
|見える情報|受領／条件不成立／対象消失／かばわれた、を区別し、失敗を単なるバグに見せない|
|状態異常|現行の強制行動・停止を迂回しない。命令しただけで解除しない|
|対象死亡|別の敵へ自然復帰、命令消費、不発のいずれかを明示。再指示の無限抽選を防ぐ|
|複数指揮官|一人の行動に矛盾する命令を重ねない。最初は指揮官一人／対象一命令|
|保存・再生|受領と消費を保存し、再読込やスピード変更で受領を引き直さない|
|適用の範囲|全体、2人回復、連鎖、ビット、R末回復へ勝手に波及させない|

新たな保存状態（誰の指令、受け手、対象、対象消失時の方針、受領／費用、期限）とコマンド・対象選択UI・リプレイ表示が必要。既存のfocusTargetIdを全味方へ読ませる一行の修正だけでは、複数対象・服従・失敗表示・合法対象の契約を表せない。

## I. 比較実験で守ること

「統率で勝てる場面」は魅力的だが、普通のSSR編成より常に強いことを前提にしない。現行AIの集中選好、石の質、必殺予約、薬、役割速度、指揮官の手数を両側で公平に扱う。意図的に分散する不利なAIをSSR側だけへ与えた図は、現行実機の結果として扱えない。概念図なら人工的な条件であることを明記し、実測勝率と呼ばない。

特にRの妨害役が敵術師を止め、Rの破砕役と別の攻撃役が同じ守りを崩すような、**役割の接続**を見せる。単体ボス一体だけ、全体一掃、圧倒的な攻撃力差など、指揮の対象変更があまり効かない盤面も残す。
